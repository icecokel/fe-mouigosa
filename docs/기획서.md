# fe-mouigosa 서비스 기획서

문서 상태: 초기 기획 · 화면 시안 구현

이 문서는 사용자가 제시한 서비스 컨셉을 기준으로 작성합니다. 명시된 요구사항과 이를 구현하기 위한 세부 기준을 정리하며, 결정되지 않은 운영 정책과 수치는 미정으로 남깁니다.

후속 [디자인 명세](디자인.md)에서 레퍼런스에 기반한 컬러·폰트·여백·반응형 기준을 정했습니다. 시각 규격은 해당 문서를 따르며, 시험 운영과 성적 산정 정책의 미정 상태는 유지합니다.

## 1. 프로젝트 개요

| 항목 | 내용 |
| --- | --- |
| 프로젝트명 | `fe-mouigosa` |
| 대상 | 프론트엔드 지식을 점검하려는 개발자 |
| 형태 | 한국식 모의고사 문제지와 OMR, 성적표로 구성된 웹페이지 |
| 핵심 컨셉 | 수능·평가원 모의고사 시험지를 웹에 옮긴 듯한 경험 |
| 경험 목표 | “수능 문제지를 펼쳤는데 과목이 프론트엔드인 느낌” |

문제를 읽고, 선택지를 검토하고, OMR을 작성한 뒤 성적표를 받는 흐름이 서비스의 중심입니다. 시험지의 시각적 형식뿐 아니라 문제와 답안을 함께 확인하는 응시 방식까지 연결합니다.

## 2. 범위와 기본 흐름

이번 기획의 범위는 시험 응시와 시험 종료 후 결과 확인입니다.

```text
문제지 확인 → 문항 풀이 및 OMR 답안 작성 → 시험 종료 → 성적표·오답 확인
```

| 단계 | 사용자가 하는 일 | 제공할 화면·정보 |
| --- | --- | --- |
| 문제지 확인 | 시험 제목과 지문을 읽는다 | 시험지 헤더, 문제 번호, 배점, 선택지 |
| 답안 작성 | 문항별 답을 고르고 답안을 확인한다 | 문제지와 연결된 OMR 선택 상태 |
| 시험 종료 | 응시를 마치고 결과로 이동한다 | 종료된 시험의 답안을 기준으로 한 결과 |
| 결과 확인 | 점수와 취약 영역, 틀린 문항을 확인한다 | 한국식 성적표와 오답 문항 |

화면 시안에는 20분 카운트다운을 표시하고 `00:00`에서 멈춥니다. OMR에서 시험을 종료하면 답안을 고정하고 성적표로 이동하며, 다시 응시할 수 있습니다. 시간 만료 후 자동 종료 여부와 최종 서비스의 시험 시작·종료 정책은 미정입니다. 회원가입, 랭킹, 문제 관리 도구 등 별도로 요청되지 않은 기능은 이 문서의 구현 범위에 포함하지 않습니다.

## 3. 시험지 화면

### 3.1 헤더

다음 문구가 시험지 상단에서 명확한 위계를 갖도록 배치합니다.

```text
2026학년도 프론트엔드 개발자 모의평가
제 1교시
프론트엔드 영역
```

연도, 교시, 영역 제목은 일반적인 앱의 페이지 제목보다 실제 시험지 표제에 가까운 크기와 정렬로 표현합니다.

### 3.2 종이와 지면 구성

- PC 시험지의 기준 비율은 A4의 가로:세로 비율인 `210:297`입니다.
- 바탕은 흰색 또는 옅은 종이색이며 본문에는 명조 계열 글꼴을 사용합니다.
- 문제는 2단으로 배치하고 여백과 가는 구분선으로 지면을 나눕니다.
- 읽는 순서는 각 지면의 왼쪽 단 위에서 아래, 오른쪽 단 위에서 아래입니다.
- 문제 번호, 지문, 코드, 선택지가 하나의 문항으로 읽히도록 묶습니다.
- 코드에는 고정폭 글꼴을 사용하고 들여쓰기와 줄바꿈을 보존합니다.
- 문항을 SaaS 스타일의 카드로 감싸거나 그림자·그라디언트로 강조하는 표현은 최대한 배제합니다.

A4는 시험지 지면의 기준입니다. 전체 시험을 한 장에 억지로 축소하지 않으며, 문항 수에 따른 지면 수와 페이지 이동 방식은 추후 결정합니다. 긴 지문이나 코드가 지면 밖으로 잘리지 않도록 해야 합니다.

### 3.3 문항 구성

| 요소 | 표시 기준 |
| --- | --- |
| 문제 번호 | 문항 앞에 숫자로 표시하고 OMR 번호와 일치시킴 |
| 지문 | 해당 문제에서 판단해야 하는 내용을 명확히 제시 |
| 배점 | 문항에 `[배점]` 형태로 표시하며, 현재 목업은 문항당 2~5점(총 62점)을 사용함 |
| 코드·조건 | 필요한 문항에 포함하고 실행 환경과 전제조건을 명시 |
| 선택지 | ①②③④⑤의 다섯 선택지를 사용 |
| 카테고리 | 시험 중에는 표시하지 않음 |

카테고리 비노출은 문제지와 OMR 모두에 적용합니다. 문제를 푸는 데 필요한 JavaScript나 React 등의 용어는 지문과 코드에 포함할 수 있습니다.

## 4. 출제 기획

### 4.1 출제 영역

카테고리는 평가하는 지식 영역입니다. JavaScript, TypeScript, React, Browser, CSS, Web Performance로 구분합니다. 현재 20개 목업 문항의 카테고리별 수는 순서대로 4·3·4·3·3·3개이며, 실제 시험의 출제 비중은 미정입니다.

### 4.2 문항 유형

| 유형 | 평가할 내용 | 문항에 필요한 조건 |
| --- | --- | --- |
| 개념 판단 | 개념과 설명의 정확성 | 옳거나 틀린 설명을 고르는 기준 |
| 결과 예측 | 코드 실행 결과 또는 화면 표시 결과 이해 | 코드·스타일과 필요한 환경 조건 |
| 타입 분석 | TypeScript 타입 추론과 검사 결과 이해 | 선언과 컴파일 조건 |
| 버그 찾기 | 원인이나 잘못된 동작 식별 | 기대 동작과 실제 코드 |
| 렌더링 횟수 예측 | 상태 변화에 따른 렌더링 이해 | React 실행 모드, Strict Mode 여부 등 결과에 영향을 주는 조건 |
| 브라우저 동작 | 브라우저의 처리 과정 이해 | 상황과 동작 판단에 필요한 전제조건 |

유형은 카테고리와 별개로 문항의 풀이 방식을 나타냅니다. 모든 유형은 ①②③④⑤ 선택지로 답하며, 5지선다는 공통 답안 형식입니다. 현재 목업의 유형별 문항 수는 개념 판단 5개, 결과 예측 7개, 타입 분석 3개, 버그 찾기 1개, 렌더링 횟수 예측 1개, 브라우저 동작 3개입니다. 실제 시험의 유형별 비중, 난이도 분포, 정답 개수 정책은 출제 전에 확정합니다.

### 4.3 문항에 필요한 정보

실제 저장 형식이나 API 스키마는 기술 설계 단계에서 정합니다. 기획상 필요한 정보는 다음과 같습니다.

- 문항 식별자와 시험 내 문제 번호
- 지문, 필요한 코드·조건, 다섯 개의 선택지
- 배점과 정답
- 카테고리와 문항 유형
- 응시자가 선택한 답안

카테고리는 결과 집계용 정보로 유지합니다. 카테고리와 유형 태그는 시험 중 화면에 노출하지 않습니다. 정답은 시험 종료 후 채점과 오답 확인에 사용하며 시험 중 화면에는 노출하지 않습니다.

## 5. OMR 답안지

### 5.1 PC

시험지 옆에 OMR 답안지를 고정합니다. 사용자가 문제지를 스크롤하는 동안에도 답안지를 확인하고 선택할 수 있어야 합니다.

```text
┌─────────────────────────────┐  ┌─────────────────┐
│     시험 제목 · 교시 · 영역     │  │    OMR 답안지    │
├──────────────┬──────────────┤  │ 문항  ①②③④⑤    │
│              │              │  │  1   ○○●○○     │
│   왼쪽 단     │   오른쪽 단    │  │  2   ○○○○○     │
│              │              │  │       …         │
└──────────────┴──────────────┘  └─────────────────┘
```

### 5.2 모바일

OMR을 화면 하단에서 열고 닫는 Drawer로 제공합니다. Drawer를 닫으면 읽던 문제로 돌아갈 수 있어야 하며, 열고 닫아도 선택한 답안은 유지합니다.

모바일의 문항 배치는 디자인 명세에 따라 767px 이하에서 1단으로 전환합니다. 768px 이상은 2단을 유지하고, OMR은 1200px 미만에서 하단 Drawer로 제공합니다. A4 지면을 화면 폭에 맞춰 무조건 축소하지 않으며, 좁은 화면에서는 읽을 수 있는 글자 크기와 자연스러운 세로 흐름을 유지합니다.

### 5.3 답안 상태와 조작

- OMR의 문제 번호와 실제 문항 번호는 항상 일치합니다.
- 답안을 입력할 수 있는 모든 위치는 동일한 답안 상태를 사용합니다.
- 선택한 답안과 미응답 상태를 명확히 구분합니다.
- 문제지 스크롤이나 Drawer 조작 때문에 답안이 초기화되지 않아야 합니다.
- 정답 여부와 영역별 분석은 시험 종료 후에 제공합니다.
- 키보드로 답안을 선택할 수 있고, 포커스와 선택 상태를 색상에만 의존하지 않고 표시합니다.
- 각 답안 입력에는 문제 번호와 선택지 번호를 구분할 수 있는 접근 가능한 이름을 제공합니다.
- 모바일 Drawer를 닫으면 포커스가 이를 연 조작 요소로 돌아가도록 합니다.

화면 시안에서는 문제지 선택지를 직접 클릭할 수 있습니다. 선택 취소 방식과 새로고침 이후 답안 복원은 미정입니다.

## 6. 시험 종료와 성적표

### 6.1 결과 화면의 형식

시험이 끝나면 한국식 성적표 형태로 결과를 보여줍니다. 표제와 선으로 구분한 표를 중심으로 구성하고, 시험지의 명조 계열 글꼴과 종이색을 이어갑니다. 영역별 수치를 여러 카드에 나누기보다 성적표의 행과 열에서 비교할 수 있도록 합니다.

### 6.2 제공할 결과

| 항목 | 사용자에게 제공할 정보 | 구현 전 결정할 내용 |
| --- | --- | --- |
| 영역별 점수 | 출제 영역별 취득 점수와 만점 | 영역 분류, 배점과 채점 규칙 |
| 백분위 | 비교 집단 안에서의 상대적 위치 | 비교 집단, 산식, 동점자 처리 |
| 등급 | 정의된 기준에 따른 등급 | 등급 수, 경계값, 절대·상대평가 여부 |
| 취약 영역 | 상대적으로 보완이 필요한 출제 영역 | 판정 지표와 기준, 문항 수가 적을 때의 처리 |
| 오답 문항 | 틀린 문제 번호와 해당 문항, 제출 답안과 정답 | 미응답 분류, 해설 제공 범위 |

시험 중 숨긴 카테고리를 결과에서는 영역별 점수와 취약 영역을 설명하는 데 활용합니다. 화면 시안은 20개 예시 문항의 정답과 배점으로 총점·영역별 점수·오답을 계산합니다. 미응답은 오답 목록에서 별도로 표시합니다. 취약 영역은 응답한 문항의 정답률이 가장 낮은 영역이며, 동률이면 함께 표시합니다. 미응답 문항은 취약 판정에서 제외합니다. 이 기준은 목업용이며 최종 성적 정책은 별도로 확정합니다.

### 6.3 결과 데이터 원칙

- 종료된 시험의 답안과 문항 배점을 기준으로 결과를 계산합니다.
- 백분위는 비교 집단의 성적 분포가 있어야 산출할 수 있습니다. 원점수를 백분위로 대신 표시하지 않습니다.
- 실제 기준이 없는 백분위·등급을 임의의 수치로 표시하지 않습니다. 취약 영역에는 화면 시안의 임시 기준을 명시합니다.
- 산출에 필요한 데이터나 정책이 없으면 해당 항목이 산출되지 않았음을 표시합니다.
- 기준이 정해지면 사용자가 결과의 의미를 이해할 수 있도록 비교 집단과 산정 기준을 안내합니다.

## 7. 반응형·가독성 기준

| 항목 | 기준 |

| 긴 코드 | 들여쓰기를 보존하고 필요한 경우 코드 영역에서 가로 스크롤을 제공 |

구체적인 글꼴, 글자 크기, 색상 값, 화면 전환 너비는 [디자인 명세](디자인.md)를 따릅니다. 본문은 나눔명조, 영역 제목은 Noto Sans KR, 기본 종이는 `#FFFFFF`로 지정합니다.

- [ ] 흰색 또는 옅은 종이색과 명조 계열 글꼴이 적용된다.
- [ ] 문항별 문제 번호, 배점, ①②③④⑤ 선택지를 확인할 수 있다.
- [ ] 지정된 출제 영역과 여러 문항 유형이 문제 구성에 반영된다.
- [ ] 코드 실행·렌더링 관련 문항에는 정답 판단에 필요한 환경 조건이 있다.
- [ ] 시험 중 문제지와 OMR에 카테고리 태그가 노출되지 않는다.
- [ ] PC에서는 문제지를 스크롤해도 고정 OMR을 사용할 수 있다.
- [ ] 모바일에서는 하단 OMR Drawer를 열고 닫으며 답안을 작성할 수 있다.
- [ ] OMR 번호와 문항 번호가 일치하고, 스크롤·Drawer 조작 후에도 답안이 유지된다.
- [ ] 키보드로 답안을 선택할 수 있으며 포커스와 선택 상태를 확인할 수 있다.
- [ ] 긴 지문·코드·선택지가 잘리지 않고 읽을 수 있다.
- [ ] 시험 종료 후 결과가 한국식 성적표 형태로 표시된다.
- [ ] 성적표에서 영역별 점수, 백분위, 등급, 취약 영역, 오답 문항을 확인할 수 있다.
- [ ] 산정 기준이나 데이터가 없는 지표는 산출되지 않은 상태로 구분된다.
- [ ] 카드를 반복하거나 그림자·그라디언트를 강조하는 SaaS 화면 표현을 최대한 배제한다.
